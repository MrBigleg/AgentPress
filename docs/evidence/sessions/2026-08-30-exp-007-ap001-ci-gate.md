## Question

Can AP-001's repository-level unit, PHP coding-standard, npm advisory, Node syntax, and deterministic-ZIP checks run green on every pull request without requiring a live WordPress or Docker service?

## Hypothesis

The scaffold's unit tests isolate compatibility logic from WordPress, PHPCS statically checks the production PHP surface, and the package builder is Node-only, so a bounded Ubuntu CI job with pinned dependency manifests should reproduce those gates while EXP-005 remains the separate WordPress runtime proof.

## Falsification condition

The hypothesis is falsified if the workflow cannot install from the committed locks, any declared check fails, two CI ZIP builds differ, the workflow requires private credentials or unpinned project dependencies, or the job is incorrectly presented as WordPress/ChatGPT/runtime evidence.

## Controls

- fixed commit/build: baseline `448e893bd2321519c7896800cc79afaa50324683` plus only the workflow/evidence change under test;
- fixed fixture/data: no WordPress database or browser fixture;
- fixed identity/capabilities: GitHub-hosted pull-request runner with default read-only repository access;
- fixed policy/configuration: committed `package-lock.json`, `agentpress/composer.lock`, PHPUnit and PHPCS configuration;
- fixed client/environment: one Ubuntu runner and explicitly selected Node/PHP versions;
- explicit scope exclusions: WordPress activation, fail-closed browser messages, WebMCP, ChatGPT, deployment, and release acceptance.

## Variables

- **Independent:** CI runner, selected Node/PHP versions, and workflow commands.
- **Dependent:** dependency installation, unit/lint/audit/syntax results, ZIP hashes, job conclusion, and PR check state.
